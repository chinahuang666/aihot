# 关键设计决策（DECISIONS）

## D1. 事件化而非文章流
聚合的核心单位是「事件」(Story)，而非原始文章 (Item)。同一事件的多篇报道合并为一个
Story，来源可展开。这是对「信息过载」的直接回应：用户看到的是信号，而不是重复头条。

## D2. 纯规则、无 LLM（默认）
摘要与「关键说法」由确定性规则生成，每条说法附带 `supportingItemIds` 证据。
- 优点：零成本、可复现、无幻觉、无隐私外发。
- LLM 为可选增强：仅当 `AIHOT_LLM_API_KEY` 且预算 > 0 时启用；任何失败都回退规则。
- 理由：MVP 阶段可靠性与成本优先；LLM 仅作为锦上添花。

## D3. 合并判定的保守主义
两个 Item 合并为同一事件的条件（任一）：
1. 内容哈希完全相同；或
2. 标题 Jaccard ≥ 0.6；或
3. 共享**产品**实体 且 标题 Jaccard ≥ 0.2；或
4. 共享**产品 + 版本** 且 标题 Jaccard ≥ 0.1。

关键护栏：
- **绝不**因共享公司名（org:）而合并（否则所有「OpenAI 新闻」会塌缩）。
- **绝不**合并来自**同一来源**的两条（同一来源的连续发布是不同事件）。
- 裸版本号碰撞（如两个不同产品的 「3.5」）若未共享产品，不合并。
目标：重复事件率 < 5%，宁可少合并也不要误合并。

## D4. 实体抽取走字典 + 版本正则，不用泛化大写词
最初尝试用「任意 PascalCase / 大写缩写」作为产品信号，导致误合并（如 `UniqueModel-0..N`
全部塌缩、或 `AI`/`LLM` 这类通用词触发合并）。改为：仅使用
(a) 版本号正则（ver:），(b) 精选产品词典（prod:），(c) 公司名仅作展示（org:，不参与合并）。

## D5. GitHub 发布源用公开 Atom Feed，而非 API
`api.github.com` 对未鉴权请求限 60 次/小时（共享出口 IP 极易触顶，实测返回 403）。
改用 `https://github.com/{owner}/{repo}/releases.atom`，免鉴权、不受该限额约束。
如未来需要更高频率，可填 `AIHOT_GITHUB_TOKEN` 回退到 API。

## D6. 聚焦近期窗口，避免历史堆积
`_focus_recent` 仅保留抓取窗口（默认 72h）内、每来源最近的 N 条（默认 20）。
早期未加此限制，单次即抓取近 1600 条历史条目，既慢又稀释信号。

## D7. 静态导出优先
前端采用 Next.js `output: export`，产物为纯静态文件，可托管于任意静态服务，
运行期零后端、零数据库——契合「零服务端静态聚合器」的定位。
